# 命令系统详解

> 本篇详细介绍 mirajay-cli 的每一个命令：用法、参数、示例和内部执行逻辑。

---

## 命令一览

| 命令 | 说明 | 使用场景 |
|------|------|----------|
| `mirajay-cli create [name]` | 初始化新项目 | 你想创建一个新项目时 |
| `mirajay-cli lint` | 代码检查 | 你想检查代码规范时 |
| `mirajay-cli build` | 构建项目 | 你想打包项目时 |
| `mirajay-cli test` | 运行测试 | 你想跑单元测试时 |
| `mirajay-cli commit` | 规范化提交 | 你想提交代码时 |
| `mirajay-cli doctor` | 环境诊断 | 你想检查环境是否就绪时 |
| `mirajay-cli deploy` | CI/CD 部署 | 你想部署项目时 |
| `mirajay-cli upgrade` | 升级脚手架 | 你想更新 mirajay-cli 本身时 |
| `mirajay-cli update-deps` | 更新模板依赖 | 维护者：更新模板中的 npm 依赖版本 |

## 一、create / init — 初始化新项目

> `create` 和 `init` 是同一个命令的两种写法。

### 基本用法

```bash
# 交互式创建（推荐新手）
mirajay-cli create my-app

# 等价于
mirajay-cli init my-app

# 一键创建（使用默认配置，跳过所有问答）
mirajay-cli create my-app -y

# 指定目标目录
mirajay-cli create my-app -d /path/to/dir

# 使用远程模板
mirajay-cli create my-app --from gh:org/repo/templates/desktop-react
```

### 参数说明

| 参数 | 简写 | 类型 | 默认值 | 说明 |
|------|------|------|--------|------|
| `name` | - | string | `my-app` | 项目名称（位置参数） |
| `--dir` | `-d` | string | 当前目录/项目名 | 目标目录 |
| `--yes` | `-y` | boolean | `false` | 跳过交互式问答 |
| `--from` | `-f` | string | - | 远程模板来源（giget 格式） |

### 交互式问答流程

```text
$ mirajay-cli create my-app

  mirajay-cli - 企业级前端脚手架
  桌面 Web · 移动端 · 微前端

? 项目名称 › my-app
? 选择项目类型 › 桌面 Web 应用
? 选择前端框架 › Vue
? 是否使用 TypeScript? › Yes
? 选择 UI 组件库 › Element Plus
? 选择 CSS 框架 › Tailwind CSS
? 是否使用 Monorepo (Turborepo) 管理? › Yes
? 选择工程化预设 › Standard（推荐）
? 选择包管理器 › pnpm（推荐）
? 是否初始化 Git 仓库? › Yes

→ 使用模板: desktop-vue
→ 配置 Monorepo 根目录 (Turborepo + pnpm workspace)...
→ 合并工程化配置 (ESLint / Prettier / Stylelint / ...)...
→ 生成 Git 配置文件 (.gitignore)...
→ 项目文件已生成到 /path/to/my-app/apps/web
→ 初始化 Git 仓库...
→ 安装依赖 (pnpm)...

✔ 项目 my-app 创建成功！

ℹ 已启用工程化: ESLint, Prettier, Stylelint, markdownlint, Vitest, commitlint, husky + lint-staged
ℹ 开发语言: TypeScript

ℹ 下一步（在浏览器中预览）:
  cd my-app
  pnpm dev  # 启动开发服务器
  → 在浏览器打开 http://localhost:5173
```

### `-y` 默认配置

使用 `-y` 时的默认配置：

```ts
{
  projectType: 'desktop',
  framework: 'vue',
  uiLibrary: 'element-plus',
  cssFramework: 'tailwindcss',
  engineering: 'standard' 预设,
  packageManager: 'pnpm',
  initGit: true,
  useMonorepo: true,
  useTypeScript: true,
}
```

### `--from` 远程模板

支持 giget 格式的远程模板源：

```bash
# GitHub
mirajay-cli create my-app --from gh:org/repo/templates/desktop-react

# GitLab
mirajay-cli create my-app --from gitlab:org/repo/templates/desktop-react

# HTTPS
mirajay-cli create my-app --from https://github.com/org/repo/archive/main.tar.gz

# 本地文件
mirajay-cli create my-app --from file:///path/to/template
```

也可以在 `.clirc.ts` 中配置远程模板映射：

```ts
export default {
  remoteTemplates: {
    'desktop-react': 'gh:org/repo/templates/desktop-react',
  }
}
```

配置后，正常使用 `mirajay-cli create my-app` 即可自动从远程拉取。

### 内部执行流程

```text
1. 打印 Banner
2. 加载 .clirc 配置
3. 交互式问答（或 -y 默认值）
4. 白名单校验（framework / uiLibrary / cssFramework / engineering.preset）
5. 确定目标目录（检查是否已存在）
6. [Flutter] 检测 Flutter SDK
7. 触发 init:before 钩子
8. 触发 init:prompts 钩子
9. [--from] 校验远程模板源
10. resolveTemplateName() 确定模板名
11. applyGitHooksForInitGit() 补全 Git hooks
12. ★ generateProject() 生成项目文件
    ├── 渲染业务模板
    ├── [Monorepo] 生成 Monorepo 布局
    ├── 合并 engineering-base 工程化配置
    ├── 合并 package.json
    └── 生成 Git hooks + .gitignore
13. [initGit] git init + git add + git commit
14. 安装依赖 (pnpm install / flutter pub get)
15. [husky] 初始化 Git hooks
16. [shadcn/ui] 安装组件
17. 触发 init:after 钩子
18. 打印成功信息 + 工程化摘要 + 下一步提示
```

## 二、lint — 代码检查

### 基本用法

```bash
# 检查所有代码
mirajay-cli lint

# 检查并自动修复
mirajay-cli lint --fix
# 或
mirajay-cli lint -f
```

### 参数说明

| 参数 | 简写 | 类型 | 默认值 | 说明 |
|------|------|------|--------|------|
| `--fix` | `-f` | boolean | `false` | 自动修复可修复的问题 |

### 执行逻辑

lint 命令会**自动检测**当前项目有哪些 lint 工具，然后逐个运行：

```text
1. 检测项目类型 (detectProjectType)
   ├── Flutter → 运行 flutter analyze
   └── 其他 → 继续检测 lint 工具

2. 检测已配置的 lint 工具 (detectAvailableLinters)
   ├── 检查 eslint.config.{js,mjs,ts} 是否存在
   ├── 检查 prettier.config.{mjs,js} / .prettierrc 是否存在
   ├── 检查 stylelint.config.{mjs,js} 是否存在
   ├── 检查 .markdownlint.json 是否存在
   └── 检查 cspell.json 是否存在

3. 如果没有任何 lint 配置 → 提示用户在 init 时选择预设
4. 逐个运行检测到的工具:
   ├── ESLint:    npx eslint . [--fix]
   ├── Prettier:  npx prettier --check . [--write]
   ├── Stylelint: npx stylelint **/*.{css,scss,vue} [--fix]
   ├── markdownlint: npx markdownlint **/*.md [--fix]
   └── cspell:    npx cspell **/*.{ts,tsx,vue,md,json}

5. 触发 lint:before / lint:after 钩子
```

> **设计亮点**：lint 命令不是"无脑运行所有工具"，而是"检测到什么就运行什么"。这样即使项目只配了 ESLint，也不会因为缺少 Stylelint 而报错。

## 三、build — 构建项目

### 基本用法

```bash
# 生产构建
mirajay-cli build

# 开发模式构建
mirajay-cli build --mode development
```

### 参数说明

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `--mode` | string | `production` | 构建模式 |

### 执行逻辑

build 命令会**自动识别**项目类型，调用对应的构建工具：

```text
1. 检测项目类型 (detectProjectType)
   │
   ├── turbo.json 存在 → Monorepo 项目
   │   └── 运行 npx turbo run build
   │
   ├── pubspec.yaml 存在 → Flutter 项目
   │   └── 运行 flutter build web --release
   │
   └── vite.config.{ts,js} 存在 → Vite 项目
       └── 运行 npx vite build --mode {production|development}

2. 触发 build:before / build:after 钩子
```

> **通俗理解**：build 命令是一个"智能代理"——它不自己构建，而是帮你找到正确的构建工具并调用它。

## 四、test — 运行测试

### 基本用法

```bash
# 运行所有测试
mirajay-cli test

# 监听模式（文件变化自动重跑）
mirajay-cli test --watch
# 或
mirajay-cli test -w

# 生成覆盖率报告
mirajay-cli test --coverage
# 或
mirajay-cli test -c
```

### 参数说明

| 参数 | 简写 | 类型 | 默认值 | 说明 |
|------|------|------|--------|------|
| `--watch` | `-w` | boolean | `false` | 监听模式 |
| `--coverage` | `-c` | boolean | `false` | 生成覆盖率报告 |

### 执行逻辑

```ts
const testArgs = ['vitest']
if (!args.watch) testArgs.push('run')        // 非监听模式加 run（跑完退出）
if (args.coverage) testArgs.push('--coverage') // 覆盖率

await runCommand('npx', testArgs, process.cwd())
```

> test 命令直接调用 Vitest。如果你的项目没有安装 Vitest，会报错。可以在 init 时选择包含 Vitest 的预设（Standard / Strict）。

## 五、commit — 规范化提交

### 基本用法

```bash
mirajay-cli commit
```

### 执行逻辑

```text
1. 检测当前项目是否配置了提交规范工具
   ├── 检查 package.json 是否有 "commit" 脚本 → 使用 cz-git
   └── 检查 commitlint.config.{cjs,js} 是否存在 → 有配置但没 cz-git

2. 如果没配置 → 提示用户在 init 时选择 Strict 预设
3. 如果配置了 cz-git → 运行 npx cz（交互式提交）
4. 如果只有 commitlint 没有 cz-git → 提示用户用 git commit 并遵循规范
```

### cz-git 交互流程

运行 `npx cz` 后，会进入交互式提交界面：

```text
? Select the type of change that you're committing:
❯ feat:     A new feature
  fix:      A bug fix
  docs:     Documentation only changes
  style:    Changes that do not affect the meaning of the code
  refactor: A code change that neither fixes a bug nor adds a feature
  perf:     A code change that improves performance
  test:     Adding missing tests or correcting existing tests
  chore:    Other changes that don't modify src or test files

? What is the scope of this change (e.g. component or file name):
? Write a short, imperative tense description of the change:
? Provide a longer description of the change:
? Are there any breaking changes? No
? Does this change affect any open issues? No
```

回答完后，自动生成符合 Conventional Commits 规范的提交信息，如：

```
feat(auth): add OAuth2 login support

Allow users to log in using Google OAuth2.
```

## 六、doctor — 环境诊断

### 基本用法

```bash
mirajay-cli doctor
```

### 检查内容

| 检查项 | 通过条件 | 失败建议 |
|--------|----------|----------|
| Node.js | >= 24.18.0 | 升级 Node.js |
| pnpm | 已安装 | `npm install -g pnpm` |
| yarn | 已安装（警告级别） | `npm install -g yarn` |
| Git | 已安装 | 安装 Git |
| Flutter SDK | 已安装（警告级别） | 安装 Flutter |

### 输出示例

```text
  mirajay-cli - 企业级前端脚手架
  桌面 Web · 移动端 · 微前端

→ 开始环境诊断...

  ✔ Node.js: v24.18.0
  ✔ pnpm: v9.15.0
  ⚠ yarn: 未安装
    npm install -g yarn
  ✔ Git: git version 2.43.0
  ⚠ Flutter SDK: 未安装（创建 Flutter 项目后需手动 flutter pub get / flutter run）
    https://flutter.dev/docs/get-started/install

ℹ 2 项警告，环境基本可用
```

> **状态说明**：
> - ✔ pass（通过）= 一切正常
> - ⚠ warn（警告）= 不影响核心功能，但某些场景可能需要
> - ✖ fail（失败）= 必须修复才能使用

## 七、deploy — CI/CD 部署

### 基本用法

```bash
# 部署到预发布环境
mirajay-cli deploy

# 部署到生产环境
mirajay-cli deploy --env production
```

### 参数说明

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `--env` | string | `staging` | 部署环境 |

### 当前状态

deploy 命令目前是一个"占位"命令，它提示用户去配置 CI/CD 流水线：

```text
→ 部署到 staging 环境...
⚠ deploy 命令需要在项目中配置 CI/CD 流水线
ℹ 模板已内置 .github/workflows/ 示例，请根据实际需求修改
ℹ 支持 GitHub Actions / GitLab CI
```

> 生成的项目中会包含 `.github/workflows/ci.yml` 模板，用户可以基于此配置自己的 CI/CD 流程。

## 九、update-deps — 更新模板依赖（维护者命令）

> 这个命令面向脚手架维护者，普通用户不需要使用。

### 基本用法

```bash
# 预览可更新的包（不写文件）
mirajay-cli update-deps --dry-run

# 一键更新所有模板中的依赖版本
mirajay-cli update-deps

# 仅更新指定包
mirajay-cli update-deps -p react -p vite

# 同时更新 CLI 自身的 package.json
mirajay-cli update-deps --include-cli

# CI 检查模式（有可更新就报错退出）
mirajay-cli update-deps --check
```

### 参数说明

| 参数 | 简写 | 类型 | 默认值 | 说明 |
|------|------|------|--------|------|
| `--dry-run` | - | boolean | `false` | 只预览不写文件 |
| `--package` | `-p` | string[] | - | 仅更新指定包（可多次指定） |
| `--include-cli` | - | boolean | `false` | 同时更新 CLI 自身 package.json |
| `--check` | - | boolean | `false` | CI 检查模式 |

### 执行逻辑

```text
1. 扫描 templates/**/package.json(.ejs) 和 src/core/engineering-manifest.ts
2. 从 npm registry 查询每个包的最新版本
3. 更新版本号，保留原有的 ^ 或 ~ 前缀
4. [--dry-run] 仅打印变更，不写文件
5. [--check] 如果有可更新项，以非 0 退出码退出（用于 CI）
```

## 命令的通用设计模式

所有命令都遵循相同的设计模式：

```ts
import { defineCommand } from 'citty'
import { banner, step, success } from '../core/logger.js'
import { hooks } from '../core/hooks.js'

export default defineCommand({
  meta: {
    name: 'xxx',
    description: 'xxx 命令描述',
  },
  args: {
    // 参数定义
  },
  async run({ args }) {
    banner()                         // 1. 打印 Banner
    await hooks.callHook('xxx:before')  // 2. 触发前置钩子

    // 3. 执行核心逻辑
    step('开始执行...')
    // ...

    await hooks.callHook('xxx:after')   // 4. 触发后置钩子
    success('完成')                     // 5. 打印成功信息
  },
})
```

> **统一模式的好处**：所有命令的结构一致，新增命令时只需要照着这个模板写核心逻辑即可。
