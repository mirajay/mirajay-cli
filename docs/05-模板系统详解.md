# 模板系统详解

> 本篇深入讲解 mirajay-cli 的模板系统：模板怎么组织的、EJS 怎么用的、文件怎么过滤的、Monorepo 怎么处理的。

---

## 一、模板系统的整体设计

### 设计理念

```text
┌──────────────────────────────────────────────────────┐
│                                                      │
│  模板 = 静态文件 + 动态变量                             │
│                                                      │
│  静态文件: 不需要修改的文件，直接复制                      │
│  动态文件: .ejs 后缀的文件，用 EJS 引擎渲染后输出          │
│                                                      │
│  渲染上下文 = 用户的所有选择 (ProjectAnswers)            │
│             + 工程化选项 (EngineeringOptions)          │
│             + 项目名称、年份等附加信息                   │
│                                                      │
└──────────────────────────────────────────────────────┘
```

### 模板分三类

```text
templates/
├── 业务模板 (18个)      ← 完整的项目骨架，每个对应一种项目类型
├── 共享模板 (3个)       ← 被业务模板"合并"进去的配置片段
│   ├── engineering-base ← 工程化配置（ESLint/Prettier/...）
│   ├── monorepo-base    ← Monorepo 根目录结构
│   └── git-base         ← .gitignore 等基础文件
```

### 文件后缀规则

| 后缀 | 处理方式 | 示例 |
|------|----------|------|
| `.ejs` | EJS 渲染后去掉 `.ejs` 后缀 | `package.json.ejs` → `package.json` |
| `.ejs.t` | EJS 渲染后去掉 `.ejs.t` 后缀 | `config.ejs.t` → `config` |
| 其他 | 直接复制 | `tsconfig.json` → `tsconfig.json` |

### 特殊文件名映射

有些工程化模板文件有多个变体，通过 `ENGINEERING_OUTPUT_MAP` 映射成统一输出名：

```text
模板文件名                           → 输出文件名
─────────────────────────────────────────────────────
eslint.react.config.js.ejs          → eslint.config.js
eslint.vue.config.js.ejs            → eslint.config.js
eslint.taro.react.config.js.ejs     → eslint.config.js
eslint.taro.vue.config.js.ejs       → eslint.config.js
eslint.uni-app.config.js.ejs        → eslint.config.js
eslint.react-native.config.js.ejs   → eslint.config.js
vitest.config.react.ts.ejs          → vitest.config.ts
vitest.config.vue.ts.ejs            → vitest.config.ts
stylelint.react.config.mjs.ejs      → stylelint.config.mjs
stylelint.vue.config.mjs.ejs        → stylelint.config.mjs
```

> **为什么这样设计？** ESLint 配置文件只能叫 `eslint.config.js`，但 React 和 Vue 需要不同的配置内容。所以模板里准备了两个变体文件，渲染时只选其中一个输出。

## 三、EJS 模板语法

### 基本语法

EJS 有三种标签：

| 标签 | 作用 | 示例 |
|------|------|------|
| `<%= 变量 %>` | 输出变量值（转义） | `<%= projectName %>` |
| `<%- 变量 %>` | 输出变量值（不转义） | `<%- readmeContent %>` |
| `<% 代码 %>` | 执行 JS 代码，不输出 | `<% if (condition) { %>` |

> **注意**：mirajay-cli 中禁用了 HTML 转义（`escape: (value) => String(value)`），所以 `<%= %>` 和 `<%- %>` 效果一样。这是为了生成代码文件时不会把 `&&` 变成 `&amp;&amp;`。

### 实际示例

#### package.json.ejs

```json
{
  "name": "<%= projectName %>",
  "version": "0.0.0",
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build"<% if (engineering.vitest) { %>,
    "test": "vitest run",
    "test:watch": "vitest"<% } %><% if (engineering.eslint) { %>,
    "lint": "eslint ."<% } %>
  }
}
```

渲染后（Standard 预设，有 Vitest 和 ESLint）：

```json
{
  "name": "my-app",
  "version": "0.0.0",
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest run",
    "test:watch": "vitest",
    "lint": "eslint ."
  }
}
```

#### vite.config.ts.ejs

```ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
<% if (cssFramework === 'tailwindcss') { %>
import tailwindcss from '@tailwindcss/vite'
<% } %>
import { resolve } from 'node:path'

export default defineConfig({
  plugins: [
    vue(),
    <% if (cssFramework === 'tailwindcss') { %>
    tailwindcss(),
    <% } %>
  ],
  resolve: {
    alias: {
      '@': resolve(__dirname, 'src'),
    },
  },
})
```

#### Home.vue.ejs

```html
<template>
  <div class="home">
    <h1><%= projectName %></h1>
    <p>欢迎使用 mirajay-cli 创建的项目</p>
  </div>
</template>

<script setup lang="ts">
// 组件逻辑
</script>

<style scoped>
.home {
  padding: 2rem;
}
</style>
```

在 EJS 模板中，你可以使用以下变量（来自 `RenderContext`）：

| 变量 | 类型 | 说明 |
|------|------|------|
| `projectName` | string | 项目名称 |
| `projectType` | string | 项目类型 (desktop/mobile/micro-frontend) |

| `uiLibrary` | string | UI 组件库 |

| `readmeCommandsSection` | string | README 命令部分内容 |
| `readmeStructureSection` | string | README 目录结构部分内容 |
| `mobilePlatform` | string | 移动端平台 |
| `microFrontendTool` | string | 微前端方案 |

| `flutterMaterial3` | boolean | Flutter Material3 |
| ... | | 其他 ProjectAnswers 字段 |

## 四、文件过滤机制

### 业务模板过滤

`getFileFilters()` 函数根据用户选择，决定跳过哪些文件：

```text
条件                                → 跳过的文件
────────────────────────────────────────────────────────────
cssFramework !== 'tailwindcss'     → 包含 "tailwind" 或 "postcss.config" 的文件
cssFramework !== 'unocss'          → 包含 "uno.config" 的文件
uiLibrary !== 'shadcn-ui'          → components/ui/*, lib/utils.*, components.json
useTypeScript === false            → tsconfig.json, *.d.ts (shadcn/ui 例外)
mobilePlatform === 'flutter'       → *.tsx, *.vue, vite.config.*
mobilePlatform === 'taro'          → 根据框架跳过不需要的入口文件
```

### 工程化模板过滤

`shouldSkipEngineeringFile()` 函数根据工程化选项，决定跳过哪些工程化文件：

```text
条件                                      → 跳过的文件
────────────────────────────────────────────────────────────
!engineering.eslint                      → 所有 eslint.* 文件
engineering.eslint 但 Profile 不匹配      → 不匹配的 eslint 变体
!engineering.vitest                      → vitest.config.*, setup.*, smoke.test.*
!engineering.stylelint                   → stylelint.* 文件
!engineering.prettier                    → prettier.config.*, .prettierignore
!engineering.markdownlint                → .markdownlint* 文件
!engineering.spellcheck                  → cspell.json 文件
!engineering.commitlint                  → commitlint.config.* 文件
!engineering.lintStaged                  → lint-staged.config.* 文件
!engineering.husky                       → .husky/* 文件
```

### 过滤执行顺序

```text
对于每个模板文件:
  1. shouldSkipFile()           ← 业务模板过滤
     └── 匹配 getFileFilters()  ← 检查 CSS/UI/TS/平台相关
  2. shouldSkipEngineeringFile() ← 工程化过滤（仅 engineeringMode）
     └── 检查 ESLint/Vitest/Stylelint/Prettier/... 相关
  3. 如果未被跳过 → 渲染或复制
```

### 变体选择逻辑

以 ESLint 为例，根据 `EngineeringProfile` 选择对应的变体：

```ts
function matchesEslintProfile(relativePath: string, profile: EngineeringProfile) {
  switch (profile) {
    case 'react':         return relativePath.includes('eslint.react.config')
    case 'vue':           return relativePath.includes('eslint.vue.config')
    case 'taro-react':    return relativePath.includes('eslint.taro.react.config')
    case 'taro-vue':      return relativePath.includes('eslint.taro.vue.config')
    case 'uni-app':       return relativePath.includes('eslint.uni-app.config')
    case 'react-native':  return relativePath.includes('eslint.react-native.config')
  }
}
```

执行时：
1. 如果 `engineering.eslint === true` → 保留匹配 Profile 的 ESLint 文件
2. 如果 `engineering.eslint === true` 但不匹配 Profile → 跳过（不输出 ESLint 配置）
3. 如果 `engineering.eslint === false` → 跳过所有 ESLint 文件

## 六、Monorepo 模板处理

### monorepo-base 模板

```text
templates/monorepo-base/
├── turbo.json                       ← Turborepo 配置
├── pnpm-workspace.yaml              ← pnpm 工作区配置
├── package.json.ejs                 ← 根目录 package.json
├── README.md.ejs                    ← 根目录 README
└── packages/
    └── shared/
        ├── package.json.ejs         ← 共享包配置
        └── src/
            └── index.ts.ejs         ← 共享包入口
```

### Monorepo 布局生成流程

```text
1. renderTemplateDir(desktop-vue, apps/web/)
   → 业务模板渲染到 apps/web/ 目录

2. finalizeMonorepoLayout()
   ├── renderTemplateDir(monorepo-base, rootDir)
   │   → 生成 turbo.json, pnpm-workspace.yaml, 根 package.json
   │
   ├── renderTemplateDir(monorepo-base/packages/shared, packages/shared/)
   │   → 生成共享包
   │
   └── mkdir apps/ packages/
       → 确保目录存在

3. mergeEngineeringToWorkspacePackages()
   → 仅向 apps/* 注入应用级工程化 scripts / 依赖（ESLint、Stylelint、Vitest）
   → packages/* 不注入
```

### 最终 Monorepo 结构

```text
my-app/
├── apps/
│   └── web/                         ← 业务代码（从 desktop-vue 渲染）
│       ├── src/
│       ├── package.json             ← ESLint / Stylelint / Vitest 依赖与脚本
│       ├── eslint.config.js         ← 框架相关配置
│       ├── stylelint.config.mjs
│       ├── vitest.config.ts
│       └── vite.config.ts
├── packages/
│   └── shared/                      ← 共享包（不单独注入 lint）
│       ├── src/index.ts
│       └── package.json
├── turbo.json                       ← Turborepo 配置
├── pnpm-workspace.yaml
├── package.json                     ← 根：turbo + Prettier/markdownlint/cspell + Git hooks
├── prettier.config.mjs              ← 全仓共享格式化
├── .editorconfig
├── .gitignore
├── .husky/                          ← Git hooks（在根目录）
│   ├── pre-commit
│   └── commit-msg
├── commitlint.config.cjs
└── lint-staged.config.mjs
```

### Monorepo 工程化的特殊处理

所有 Monorepo 模板（桌面/移动勾选 Monorepo、以及 Module Federation）统一分层：

```text
非 Monorepo:
  工程化配置和依赖全部注入到项目根目录

Monorepo（含 MF）:
  ├── 根目录
  │   ├── Prettier / EditorConfig / markdownlint / cspell（共享规范）
  │   └── commitlint / husky / lint-staged（仓库级 hooks）
  ├── apps/web 或 apps/host
  │   └── ESLint / Stylelint / Vitest（框架相关配置与依赖）
  └── packages/*  ← 不注入 lint（避免无配置却装依赖）
```

> **为什么这样分？** 格式化与提交规范是全仓一份；ESLint/Stylelint/Vitest 随框架 profile 落在应用包。根目录 `pnpm lint` 仍走 Turborepo，由各 `apps/*` 执行本包 lint。

### 根目录资源如何被用到？子包如何互相引用？

生成物是典型的 **pnpm workspace + Turborepo**。这里分清两件事：根上放的是「全仓工具与配置」，包之间传的是「业务模块」。

#### 1. 子包如何用到根目录的资源

子包一般**不会** `import '../../../prettier.config.mjs'`，而是通过下面三种机制「看见」根：

**A. pnpm 工作区 + 依赖提升**

```yaml
# pnpm-workspace.yaml（在仓库根）
packages:
  - 'apps/*'
  - 'packages/*'
```

在**仓库根**执行 `pnpm install` 后：

- 根 `package.json` 里的 `prettier`、`turbo`、`husky` 等装在根
- 子包执行由根编排的脚本时，会解析到这些工具
- 各包自己的运行时依赖仍写在各自的 `package.json`（不要把业务库只装在根上当隐式依赖）

**B. 配置文件向上查找**

| 工具 | 常见行为 |
|------|----------|
| Prettier | 从文件目录向上找 `prettier.config.*`，根上一份即可管全仓 |
| EditorConfig | 同样向上找 `.editorconfig` |
| ESLint flat | 在本包 cwd 找 `eslint.config.js`（脚手架放在 `apps/web` 或 `apps/host`） |

因此：根上跑 `pnpm format` 会格式化 `apps/**`、`packages/**`；在 `apps/web` 里跑 `pnpm lint` 则用该包自己的 ESLint 配置。

**C. 根脚本只负责编排，不直接 import 业务源码**

```json
// 根 package.json（示意）
{
  "scripts": {
    "dev": "turbo run dev",
    "lint": "turbo run lint",
    "format": "prettier --write ."
  }
}
```

- `turbo run lint` → 进入声明了 `lint` 的包（如 `apps/web`）执行本包脚本
- `prettier --write .` → 在根用根配置扫全仓文件

```text
仓库根
├── package.json / prettier.config.mjs / .husky/   ← 工具与规范
├── apps/web/          ← 业务 + 框架级 lint
└── packages/shared/   ← 共享模块（见下一节）
```

#### 2. 一个包如何调用另一个包

业务上的包间引用靠 **`workspace:` 协议 + 包名导入**，而不是相对路径穿透目录。

**声明依赖**（脚手架在勾选 Monorepo 时已写好）：

```json
// apps/web/package.json
{
  "dependencies": {
    "@my-app/shared": "workspace:*"
  }
}
```

```json
// packages/shared/package.json
{
  "name": "@my-app/shared",
  "exports": {
    ".": "./src/index.ts"
  }
}
```

`workspace:*` 表示：不要去 npm 下载，链接本仓库里同名的 workspace 包。

**代码中引用：**

```ts
// apps/web/src/App.tsx
import { formatDate } from '@my-app/shared'
```

解析链路：

1. 打包器 / Node 看到包名 `@my-app/shared`
2. pnpm 在 `apps/web/node_modules/@my-app/shared` 建软链 → `packages/shared`
3. 按 `exports` / `main` 进入 `src/index.ts`
4. 开发时 Vite 通常直接消费源码（改 shared 保存后 web 即可用到）

安装后可用下列命令自检：

```bash
# 在仓库根
pnpm install
ls -la apps/web/node_modules/@my-app/shared
# 应指向 ../../../../packages/shared（符号链接）

pnpm why @my-app/shared --filter web
# 应显示 link:../../packages/shared
```

**推荐与禁忌：**

| 场景 | 做法 |
|------|------|
| `apps/web` → `packages/shared` | web 声明 `workspace:*`，再 `import from '@xxx/shared'` |
| 再加一个 `apps/admin` | admin 同样声明对 shared 的 `workspace:*` |
| `packages/ui` → `packages/shared` | ui 的 `package.json` 依赖 shared，再被 apps 依赖 |
| 避免 | shared 依赖 apps（循环）；用 `../../../packages/shared` 当常规写法 |

> Module Federation 的 `apps/host` 与 `packages/remote-app` 同样是 workspace 包；运行时的远程加载是 Federation 另一层机制，与 `workspace:*` 的编译期链接不同。

#### 3. 动手串一遍（生成项目后）

```bash
cd my-app
pnpm install                 # 建立 workspace 链接
pnpm format                  # 根 Prettier + 根配置
# 在 apps/web 中: import { formatDate } from '@my-app/shared'
pnpm build                   # 根 turbo → apps/web 构建并解析 shared
```

一句话：**根靠「命令 + 配置上溯」服务全仓；包与包靠 `workspace:*` + 包名 `import`。**

## 七、远程模板

### giget 下载机制

```text
用户执行:
  mirajay-cli create my-app --from gh:org/repo/templates/desktop-react

内部流程:
  1. validateRemoteTemplateSource()  → 校验格式 + 防注入
  2. getCacheDir()                   → 计算缓存路径
     ~/.cache/mirajay-cli/templates/{hash}/
  3. downloadTemplate()              → giget 下载
  4. 返回下载后的本地路径
  5. 用这个路径代替本地 templates/ 目录
```

### 支持的远程源

| 前缀 | 平台 | 示例 |
|------|------|------|
| `gh:` | GitHub | `gh:org/repo/templates/desktop-react` |
| `gitlab:` | GitLab | `gitlab:org/repo/templates/desktop-react` |
| `bitbucket:` | Bitbucket | `bitbucket:org/repo/templates/desktop-react` |
| `git:` | Git 仓库 | `git:https://github.com/org/repo.git` |
| `https://` | HTTPS | `https://github.com/org/repo/archive/main.tar.gz` |
| `file://` | 本地文件 | `file:///path/to/template` |

### 缓存机制

- 缓存目录：`~/.cache/mirajay-cli/templates/{sha256_hash}/`
- 第二次下载同一模板时，直接从缓存读取
- 可通过 `.clirc` 的 `templateCacheDir` 自定义缓存目录

## 八、添加新模板

如果你想为脚手架添加一个新的业务模板，步骤如下：

### 步骤 1：创建模板目录

```bash
mkdir templates/my-new-template
```

### 步骤 2：编写模板文件

```text
templates/my-new-template/
├── package.json.ejs       ← 用 <%= projectName %> 等变量
├── vite.config.ts.ejs
├── index.html.ejs
├── tsconfig.json          ← 不需要变量的直接放
└── src/
    ├── main.ts.ejs
    └── App.vue.ejs
```

### 步骤 3：注册模板名解析

在 `src/core/template.ts` 的 `resolveTemplateName()` 中添加：

```ts
if (answers.projectType === 'my-type') {
  return 'my-new-template'
}
```

### 步骤 4：添加交互选项

在 `src/core/prompts.ts` 中添加对应的交互问题。

### 步骤 5：更新类型定义

在 `src/types.ts` 中添加新的项目类型（如果需要）。

### 步骤 6：添加测试

在 `tests/` 目录下添加测试用例。

### 步骤 7：测试

```bash
pnpm build
mirajay-cli create test-app
# 选择你新添加的项目类型，验证生成结果
```
